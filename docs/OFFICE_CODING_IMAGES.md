# Image-aware Office coding requests (review prerequisite)

`/code` now carries the owner's prompt and selected PNG/JPEG screenshots through the private coding request contract. Ordinary chat and its mailbox attachments are unchanged. The Office layout is unchanged. The hosted coding endpoint is still disabled by default: this PR includes the private relay and outbound worker code, but does **not** configure Access/keys, connect Pages to Tim's Codex account, install a service, or deploy anything.

## Verified implementation

- An authenticated, same-origin coding request resolves its provider/session/repository/branch from server-owned identity. Up to four PNG/JPEG images are accepted, at most 4 MB each / 8 MB total. Request reading is bounded. Filename, MIME/header, size and canonical base64 checks precede storage; PNG dimensions are bounded. Arbitrary URLs, filesystem paths, SVGs and unsupported providers are rejected.
- Image bytes are persisted privately before dispatch. Durable HTTP jobs contain immutable SHA-256 attachment references, names, types and lengths. Private SQLite image keys include owner, tenant, provider, conversation, request, session and repository/branch. They are not public URLs and no image retrieval endpoint is installed.
- The native adapter re-reads and hashes every image before constructing Codex `turn/start` input containing the text and distinct `{type: 'image', url: 'data:image/...;base64,...'}` entries. An unavailable or altered image stops the turn; there is no text-only fallback. Repeated sends bind both prompt and exact attachments to one request ID.
- A native `office_route` tool reports a concise proposed approach and typed outcome. A coding request does not inherently mean a PR. Only a completed, explicitly selected draft route with a clean baseline and native-attested, verified intended diff can call the fixed draft publisher. Diagnosis/local/clarification, no-op, failed/interrupted and unknown routes do not publish. Durable publication claims prevent uncertain writes from replaying. Explicit `/code /pr` remains available for the scoped publisher; a `/pr` accompanied by images enters the coding session instead of bypassing image inspection.
- Native approval requests remain owner decisions; default handling cancels. The CLI adapter requires installed Codex 0.169.0 and positively verified included ChatGPT usage without paid credits. No browser credentials, mailbox/log dispatch, watcher changes, permission expansion, merge or deploy.
- Errors preserve the browser draft and attachments. Successful acceptance clears them; an accepted but subsequently uncertain turn is not automatically replayed. State lives in private SQLite and native Codex's usual private session storage, not browser localStorage. Production storage retention/deletion must be specified when provisioning a hosted relay.

## Hosted transport: implemented, not activated

The deployed default remains disconnected. The Pages route calls the new hosted factory only with the explicit `OFFICE_CODING_RELAY_ENABLED=reviewed-v1` marker **and** complete scope/identity/signing configuration. Shared chat codes and mailbox tokens never establish coding authorization. There are no current production values for this configuration.

The handler validates a standard signed Access assertion against the configured team issuer, application audience and exact owner subject. It rejects wrong algorithms, expired assertions and email/header-only identity. It signs a ten-minute, one-worker job envelope containing the exact owner/session/repository/branch, prompt and image hashes. A separate worker signing key authenticates results back to the page. No Access token, signing key or native transcript is placed in the mailbox.

The existing private `tpruittguitar/office-mailbox` can hold the coding-only `coding-v1/` namespace; `agent-chat/` is never touched. Images are private immutable files, verified against the signed job. Jobs become ready only after every image is persisted. The outbound worker checks the repository is still private, both signed admission and ready records match, scope/worker/expiry and image hashes match, then creates a permanent execution marker using GitHub's create-only Contents operation. Existing files cannot be overwritten without their blob SHA. Worker status uses SHA-conditional updates. Conflicts and uncertain writes do not retry execution. A private SQLite claim ledger additionally blocks replay after a remote marker is deleted; a SQLite worker lock serializes the dedicated workspace across processes. Crash locks and claims are never automatically reclaimed.

This is **at-most-once dispatch with possible stuck/unknown jobs**, not guaranteed eventual execution. If the worker crashes after claiming, an operator must reconcile the existing native session rather than resend or erase the ledger. Run one designated worker with one persistent private ledger; do not clone/reset that ledger or horizontally scale the same worker identity. GitHub history retains image bytes even after deleting a file. Treat the mailbox as private retained task data; agree on retention before activation. A 1,000-ready-file backlog fails closed for reconciliation rather than silently skipping work.

Tests model GitHub's create/expected-SHA conflict behavior, including two independent local workers racing one job, lost claim responses, remote marker deletion, forged/expired/foreign jobs, modified images and forged results. They do not write to the actual mailbox. The actual 3D browser can run the entire Access-assertion fixture → hosted handler → mailbox double → outbound worker → native-adapter fixture path with `OFFICE_RELAY_BROWSER=1`; it verifies exact image bytes and preserves the expired-auth draft. Native RPC and forge publication in this hosted-path test are mocked.

## Actual native visual proof (2026-11-22)

A separate temporary TIMMAY proof used these service/store/image/adapter modules with the installed Codex app-server and the already signed-in included ChatGPT subscription. The same dummy screenshot used by the browser fixture had SHA-256 `d36ebd8b67e3e6c4c8307abae37436a1e138d5d6efd47d9b8dd1d4731a088ba4`. The prompt asked for the marked text and color without supplying either answer. The real native session chose diagnosis, proposed inspecting the screenshot, then correctly reported “Triangle 731” and a red oval. Status was `finished`, no approval was needed, no draft was published, and the dedicated scratch workspace remained empty. The native process was closed after the proof. This verifies actual image understanding through the local adapter; it does not prove or activate a hosted relay. Browser coverage uses mock native RPC; native coverage uses the real app-server through the service in a separate controlled proof.

Mailbox privacy is the existing private repository's access boundary: authorized repository readers can read stored prompts and screenshots. This implementation does not claim encryption against those readers or introduce per-file GitHub ACLs. Only the configured owner/tenant is admitted by the hosted handler, and other mailbox writers cannot forge signed coding requests or results. The outbound runner opens the SQLite ledger without startup recovery, so a second process cannot rewrite an active native record before obtaining its workspace lock.

## Path-only Access and sign-in readiness

The exact production destination is `foreman-cockpit.pages.dev/api/agent-coding`. It covers both the coding API and its read-only `?signin=1` handoff because Access does not distinguish query strings. No additional protected path is needed. Keep `/office`, `/office.html`, `/office/*` assets, `/api/agent-chat` and the rest of the site outside this Access application. Do not protect the entire hostname or use the unnecessarily broad `/api/*` pattern.

Cloudflare documents a supported setup for production `pages.dev` hosts: bootstrap the Pages Access application, then edit the preview wildcard hostname to the production hostname. Its separate application-path documentation supports protecting just a path. The smallest candidate combines those steps: in the generated application, remove the preview wildcard and set the coding-only path **in the same saved configuration**, with an Allow policy for the confirmed owner. Do not save a hostname-wide production rule first. Do not re-enable a separate preview policy unless preview protection is also explicitly requested. If the account UI/API cannot save that combined production-host/path destination, stop and report that limitation instead of changing domains or locking the whole Office.

This combined setup is documented capability, **not a proven configured application on this account**. The latest read-only Access API check still returned `access.api.error.not_enabled`. No Access enrollment, policy, destination, paid plan, billing change or domain migration was performed. Plan eligibility and the owner's chosen identity provider/verified identity still need confirmation. Cloudflare's preview-policy toggle alone does not protect the production hostname.

Expired Access redirects are not safely handled by treating a failed `fetch` as a login. The client now refuses to follow API redirects (including POSTs carrying screenshots) and offers an explicit **Sign in to coding** action in the existing footer. Clicking it opens the fixed same-origin `/api/agent-coding?signin=1` URL in a separate `noopener,noreferrer` tab. The original page remains open with its in-memory draft, image and retry ID. After Access authentication, the handoff verifies the configured owner and explains how to return; it reads/writes no mailbox data and submits nothing. There is no automatic retry. The owner returns and presses Send when a draft remains; the request ID is reused. Already accepted jobs can resume ordinary status polling. The page does not promise preservation if the original tab is reloaded or closed.

The full browser fixture exercises an expired POST redirect, deliberate sign-in click, separate tab with no opener, simulated Access completion, unchanged screenshot/draft, zero dispatch from login GET, and exactly one additional dispatch only after explicit Send. It does not claim actual Cloudflare session-cookie or identity-provider verification on this account.
